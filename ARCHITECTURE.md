# Architecture

gentle-claude is a Claude Code plugin that wires the gentle-ai ecosystem into Claude Code
via hooks. It mirrors what gentle-pi does for Pi, adapted for Claude Code's extension model.

## Layers

```
Claude Code (host)
    │
    └── gentle-claude plugin          ← this repo
            │
            ├── hooks (bash scripts)  ← lifecycle integration
            ├── skills/               ← Claude Code harness identity
            ├── prompts/              ← Claude Code adapted workflows
            │
            ├── gentle-ai CLI         ← review lifecycle engine (PATH dep)
            │
            └── vendor/gentle-pi/     ← sparse submodule (read-only reference)
                    ├── skills/       ← platform-agnostic skill definitions
                    ├── prompts/      ← Pi prompts (not injected — Pi-specific paths)
                    ├── contracts/    ← review integration contract v1
                    └── assets/       ← orchestrator sub-assets and chains
```

## Hook flow

Claude Code fires hooks at lifecycle boundaries. gentle-claude handles four:

| Hook | Script | Responsibility |
|---|---|---|
| `SessionStart` | `session-start.sh` | ecosystem health check (gentle-ai + codegraph) |
| `UserPromptSubmit` | `user-prompt-submit.sh` | inject skill registry + asset manifest + review status |
| `PreToolUse` | `pre-tool-use.sh` | classify diff tier, classify command, gate git commit |
| `Stop` | `session-stop.sh` | async post-session cleanup |

Two additional hooks handle edge cases:

- `PostCompaction` → `post-compaction.sh` — re-injects context after Claude compacts memory
- `SubagentStop` → `subagent-stop.sh` — handles subagent lifecycle cleanup

## Skill registry injection

`user-prompt-submit.sh` builds the skill context in three layers, in priority order:

```
1. Official registry (.atl/skill-registry.md)
   Generated by `gentle-ai skill-registry refresh`.
   Scans project-level (skills/, .claude/skills/) and user-level (~/.claude/skills/) paths.

2. Plugin skills (plugin/claude-code/skills/)       scope: "plugin"
   Claude Code-specific skill definitions not in the official registry.
   Current: skills/gentle-ai/SKILL.md (harness identity).

3. Vendor skills (vendor/gentle-pi/skills/)         scope: "adapter"
   Platform-agnostic skills from gentle-pi, appended after plugin skills.
   Skipped if a same-named skill already exists in layers 1 or 2.
```

This is implemented in `inject_adapter_skills()` — a single encapsulated function.
If gentle-ai adds native support for vendor/ paths, remove this function and nothing else changes.

## Vendor layer (gentle-pi submodule)

`vendor/gentle-pi` is a sparse git submodule pointing to
[Gentleman-Programming/gentle-pi](https://github.com/Gentleman-Programming/gentle-pi).

**Why sparse?** gentle-pi is an npm package with a full TypeScript runtime (`lib/`,
`extensions/`, `scripts/`). None of that applies to Claude Code. Sparse checkout
materializes only the four directories that are platform-agnostic:

| Directory | What it contains | Used by |
|---|---|---|
| `skills/` | LLM-first skill definitions | `inject_adapter_skills()` |
| `contracts/` | Review integration contract v1 | gentle-ai CLI |
| `assets/` | Orchestrator sub-assets, chains | `inject_asset_manifest()` |
| `prompts/` | Operational prompt templates | reference only (Pi-specific paths) |

**What is NOT materialized:**
- `lib/` — TypeScript review implementation (Pi runtime)
- `extensions/` — Pi TUI extensions
- `scripts/` — Node.js build and installer scripts
- `runtime/`, `themes/`, `openspec/` — Pi internal infrastructure

**Pi-context filter:** vendor assets occasionally reference Pi-specific identifiers
(`subagent_run`, `~/.pi/`, Pi mono-repo paths). The `## Vendor asset context` section
in `skills/gentle-ai/SKILL.md` documents exactly which references are Pi-only so agents
can apply vendor assets without confusion.

**Updating the vendor:** run `git submodule update --remote vendor/gentle-pi` to pull
the latest gentle-pi commit, then commit the updated submodule pointer.

## Asset lazy-loading

`inject_asset_manifest()` in `user-prompt-submit.sh` emits a path manifest per prompt:

```
## Adapter Assets

Load the file when the workflow applies — do not preload.
- Delegation rules: `vendor/gentle-pi/assets/orchestrator-delegation.md`
- Memory protocol:  `vendor/gentle-pi/assets/orchestrator-memory.md`
- Skills discovery: `vendor/gentle-pi/assets/orchestrator-skills.md`
- SDD workflow:     `vendor/gentle-pi/assets/sdd-orchestrator-workflow.md`
- Chain — 4R review:  `vendor/gentle-pi/assets/chains/4r-review.chain.md`
...
```

Agents load the file content only when the relevant workflow is triggered.
`orchestrator.md` is intentionally excluded — it contains Pi-specific identity
contracts that don't apply to Claude Code.

## Local skills vs vendor skills

Two skill directories exist, each with a different purpose:

| Path | Purpose |
|---|---|
| `plugin/claude-code/skills/gentle-ai/SKILL.md` | Claude Code harness identity. Defines this plugin as a gentle-ai adapter, not a Pi harness. Always wins over the same-named vendor skill. |
| `vendor/gentle-pi/skills/gentle-ai/SKILL.md` | Pi harness identity. Injected only when no plugin-level `gentle-ai` skill exists (dedup rule). |

The same pattern applies to any future skill where Claude Code behavior diverges from Pi.

## Runtime dependencies

| Dependency | Required | Purpose |
|---|---|---|
| bash | yes | hook scripts |
| jq | yes | JSON parsing in hooks |
| gentle-ai CLI | yes | review lifecycle, skill-registry refresh, doctor |
| codegraph | recommended | structural codebase analysis |
| bats-core | dev only | test suite (installed via `tests/install-deps.sh`) |
| Node.js / npm | no | gentle-pi is vendored; no JS runtime needed |
